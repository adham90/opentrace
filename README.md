# OpenTrace

A self-hosted, connector-based debugging and monitoring engine. Connect your production data sources — logs, databases, monitoring — and let AI-powered watchers automatically detect anomalies, surface alerts, and help you debug issues faster.

![OpenTrace UI Walkthrough](docs/screenshots/opentrace-ui-walkthrough.gif)

## Features

- **Log Ingestion & Search** — Ingest logs via HTTP API, search with full-text search (FTS5), filter by service, level, and environment
- **Database Connectors** — Connect read-only to your PostgreSQL databases and run safe, validated queries
- **AI-Powered Watchers** — Set up automated monitors that use LLMs to analyze your logs and detect anomalies on a schedule, with cron expression support for precise scheduling
- **Alerts Dashboard** — View, read, and dismiss alerts generated by watchers
- **MCP Server** — Expose all tools via Model Context Protocol for use with Claude Code, Claude Desktop, and other MCP-compatible clients
- **Server Monitoring** — Lightweight agent collects CPU, memory, disk, network, and load metrics from your VMs and pushes them to the dashboard
- **Safety Guardrails** — SQL validation ensures only SELECT queries run, with configurable timeouts and row limits

## Quick Start

### Prerequisites

- **Go 1.24+** (for building from source)
- **Ollama** (optional, for local LLM — `ollama serve`)

### Build & Run

```bash
# Clone the repository
git clone https://github.com/adham90/opentrace.git
cd opentrace

# Copy environment config
cp .env.example .env

# Build
go build -o opentrace ./cmd/opentrace

# Run
./opentrace
```

Open [http://localhost:8080](http://localhost:8080) in your browser.

### Docker Compose (Full Stack)

```bash
docker-compose up
```

This starts:
- **OpenTrace** on `localhost:8080`
- **PostgreSQL** on `localhost:5432` (for database connectors)
- **Ollama** on `localhost:11434` (local LLM)

## Configuration

All configuration is via environment variables. Copy `.env.example` to `.env` and adjust:

| Variable | Default | Description |
|---|---|---|
| `OPENTRACE_DATA_DIR` | `~/.opentrace` | Directory for SQLite database |
| `OPENTRACE_LISTEN_ADDR` | `:8080` | HTTP server listen address |
| `OPENTRACE_API_KEY` | _(empty)_ | Bearer token for log ingestion API (optional) |
| `OPENTRACE_LLM_PROVIDER` | `ollama` | LLM backend: `ollama`, `anthropic`, `openai` |
| `OPENTRACE_OLLAMA_URL` | `http://localhost:11434` | Ollama endpoint |
| `OPENTRACE_OLLAMA_MODEL` | `llama3.2` | Ollama model name |
| `OPENTRACE_ANTHROPIC_API_KEY` | _(empty)_ | Anthropic API key (for Claude) |
| `OPENTRACE_ANTHROPIC_MODEL` | `claude-sonnet-4-5-20250929` | Claude model |
| `OPENTRACE_OPENAI_API_KEY` | _(empty)_ | OpenAI API key |
| `OPENTRACE_OPENAI_MODEL` | `gpt-4o` | OpenAI model |
| `OPENTRACE_MAX_QUERY_ROWS` | `500` | Max rows returned from SQL queries |
| `OPENTRACE_STATEMENT_TIMEOUT_MS` | `5000` | SQL query timeout in milliseconds |
| `OPENTRACE_MAX_AGENT_STEPS` | `12` | Max iterations in the AI agent loop |
| `OPENTRACE_MAX_TOOL_CALLS` | `8` | Max tool calls per agent turn |
| `OPENTRACE_METRIC_RETENTION_DAYS` | `7` | Days to retain server metrics before pruning |
| `OPENTRACE_DEV` | `false` | Enable live template reloading |

### Web UI

The web UI is available at `http://localhost:8080` with these pages:

| Page | Path | Description |
|---|---|---|

| Watchers | `/watchers` | Create and manage automated monitors |

### Ingesting Logs

Send logs to OpenTrace via HTTP:

```bash
curl -X POST http://localhost:8080/api/logs \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -d '{
    "service": "payment-api",
    "level": "error",
    "message": "Payment gateway timeout after 30s",
    "environment": "production",
    "metadata": {"transaction_id": "tx_abc123"}
  }'
```

### REST API

**Connectors:**
```
POST   /api/connectors           # Create a connector
GET    /api/connectors           # List all connectors
POST   /api/connectors/{id}/test # Test connectivity
DELETE /api/connectors/{id}      # Delete a connector
```

**Logs:**
```
POST   /api/logs                 # Ingest log entries
GET    /api/logs                 # Search/filter logs
```

**Watchers:**
```
POST   /api/watchers             # Create a watcher
GET    /api/watchers             # List all watchers
GET    /api/watchers/{id}        # Get a specific watcher
PUT    /api/watchers/{id}        # Update a watcher
DELETE /api/watchers/{id}        # Delete a watcher
POST   /api/watchers/{id}/pause  # Pause a watcher
POST   /api/watchers/{id}/resume # Resume a watcher
POST   /api/watchers/{id}/run    # Trigger a manual run
GET    /api/watchers/{id}/runs   # List run history
```

#### Monitor Scheduling

Monitors support two scheduling modes:

**Simple intervals** (default) — set via `time_range`:
```json
{"time_range": "15m"}
```

**Cron expressions** — set via `schedule` for precise control:
```json
{
  "time_range": "1h",
  "schedule": "0 9 * * 1-5"
}
```

When `schedule` is set, it controls **when** the monitor runs. The `time_range` field becomes just the log lookback window. When `schedule` is not set, `time_range` is used for both.

Supported schedule formats:

| Format | Example | Description |
|---|---|---|
| Simple interval | `5m`, `1h`, `30s` | Run every N seconds/minutes/hours |
| 5-field cron | `0 9 * * *` | Daily at 9:00 AM UTC |
| Weekday cron | `0 9 * * 1-5` | Weekdays at 9:00 AM UTC |
| Business hours | `*/15 8-17 * * 1-5` | Every 15 min, Mon-Fri 8am-5pm |
| Predefined | `@hourly`, `@daily`, `@weekly` | Standard intervals |
| Every duration | `@every 30s` | Run every 30 seconds |

**Alerts:**
```
GET    /api/alerts               # List alerts (paginated)
GET    /api/alerts/count         # Get unread alert count
POST   /api/alerts/{id}/read     # Mark alert as read
POST   /api/alerts/{id}/dismiss  # Dismiss an alert
```

**Servers:**
```
POST   /api/servers/register     # Register a server (agent self-registration)
POST   /api/servers/{id}/metrics # Push metric batch from agent
GET    /api/servers              # List all servers
GET    /api/servers/{id}         # Get server details
DELETE /api/servers/{id}         # Remove a server
GET    /api/servers/{id}/metrics # Query metrics (time range, metric name)
```

**Health:**
```
GET    /healthz                  # Health check
```

## MCP Server Integration

OpenTrace includes a built-in [Model Context Protocol (MCP)](https://modelcontextprotocol.io) server. This lets AI tools like **Claude Code**, **Claude Desktop**, **Cursor**, and other MCP-compatible clients directly query your logs, search your databases, and manage watchers — all through natural language.

### Available MCP Tools

| Tool | Description |
|---|---|
| `log_search` | Search logs with filters (service, level, environment, query) |
| `db_search` | Run read-only SQL queries against connected databases |
| `db_schema` | Inspect database schema (tables, columns, types) |
| `list_connectors` | List all registered data source connectors |
| `list_watchers` | List configured watchers and their status |
| `create_watcher` | Create a new automated watcher (supports cron schedules) |
| `list_alerts` | List recent alerts |
| `list_servers` | List all monitored servers with status |
| `query_metrics` | Query time-series metrics for a server |
| `server_health` | Get current health snapshot for a server |

### Using with Claude Code

1. **Build the binary** (if not already built):

```bash
go build -o opentrace ./cmd/opentrace
```

2. **Create a launcher script** (`run-mcp.sh`):

```bash
#!/bin/bash
cd /path/to/opentrace
set -a
source .env
set +a
exec ./opentrace mcp
```

```bash
chmod +x run-mcp.sh
```

3. **Add to your project's `.mcp.json`** (in your project root):

```json
{
  "mcpServers": {
    "opentrace": {
      "type": "stdio",
      "command": "/path/to/opentrace/run-mcp.sh",
      "args": []
    }
  }
}
```

4. **Start Claude Code** — OpenTrace tools will be available automatically. You can ask things like:

> "Search my logs for payment errors in the last hour"
>
> "Show me the schema of the users table"
>
> "Create a watcher that checks for 500 errors every 15 minutes"

### Using with Claude Desktop

Add the server to your Claude Desktop config (`~/Library/Application Support/Claude/claude_desktop_config.json` on macOS):

```json
{
  "mcpServers": {
    "opentrace": {
      "command": "/path/to/opentrace/run-mcp.sh",
      "args": []
    }
  }
}
```

Restart Claude Desktop and OpenTrace tools will appear in the tools menu.

### Using with Cursor

In Cursor settings, add an MCP server:

- **Name:** `opentrace`
- **Type:** `stdio`
- **Command:** `/path/to/opentrace/run-mcp.sh`

### Using with Any MCP Client

OpenTrace's MCP server communicates via **stdio** using JSON-RPC. Start it with:

```bash
./opentrace mcp
```

This reads from stdin and writes to stdout. All application logs go to stderr to keep the JSON-RPC channel clean.

## VM Metrics Agent

OpenTrace includes a lightweight agent that runs on your servers, collects system metrics, and pushes them to the dashboard. When servers are monitored, watcher LLM agents automatically get access to infrastructure tools for correlating log anomalies with server health.

### Collected Metrics

| Category | Metrics |
|---|---|
| **CPU** | `cpu.usage_percent`, `cpu.user_percent`, `cpu.system_percent`, `cpu.idle_percent` |
| **Memory** | `memory.total_bytes`, `memory.used_bytes`, `memory.available_bytes`, `memory.usage_percent` |
| **Swap** | `swap.total_bytes`, `swap.used_bytes`, `swap.usage_percent` |
| **Disk** | `disk.total_bytes`, `disk.used_bytes`, `disk.usage_percent` (per mount) |
| **Network** | `network.bytes_sent_per_sec`, `network.bytes_recv_per_sec` (per interface) |
| **Load** | `load.1m`, `load.5m`, `load.15m` |
| **System** | `process.count`, `uptime.seconds` |

### Running the Agent

```bash
OPENTRACE_SERVER_URL=http://your-opentrace-host:8080 \
OPENTRACE_API_KEY=your-api-key \
opentrace agent
```

### Agent Configuration

| Variable | Default | Description |
|---|---|---|
| `OPENTRACE_SERVER_URL` | _(required)_ | URL of your OpenTrace server |
| `OPENTRACE_API_KEY` | _(empty)_ | API key for authentication |
| `OPENTRACE_AGENT_INTERVAL` | `30s` | Metrics collection interval |

### Running as a Systemd Service

Create `/etc/systemd/system/opentrace-agent.service`:

```ini
[Unit]
Description=OpenTrace Agent
After=network.target

[Service]
Type=simple
Environment=OPENTRACE_SERVER_URL=http://your-opentrace-host:8080
Environment=OPENTRACE_API_KEY=your-api-key
ExecStart=/usr/local/bin/opentrace agent
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable --now opentrace-agent
```

### Updates

OpenTrace checks for new versions automatically. When an update is available, a banner appears at the top of the dashboard with a link to the release notes.

**Auto-updates (Docker):** Use `docker-compose.prod.yml` which includes Watchtower — it checks for new images hourly and restarts automatically.

**Manual update (Docker):** `docker compose pull && docker compose up -d`

**Manual update (binary):** Download the new release and restart the service.

### Data Storage

OpenTrace stores all data in a SQLite database at `~/.opentrace/opentrace.db` (configurable via `OPENTRACE_DATA_DIR`). The database uses WAL mode for concurrent read access. Back up this single file to preserve all your connectors, logs, watchers, and alerts.

## Architecture

```
  ┌──────────────┐                    ┌─────────────────────────────────┐
  │  VM Agent    │──push metrics──▶   │          Web UI (HTMX)           │
  │  (gopsutil)  │                    │ Alerts | Watchers | Logs | Servers│
  └──────────────┘                    └──────────────┬──────────────────┘
                                                     │
                                      ┌──────────────▼──────────────────┐
                                      │        HTTP Server (Chi)         │
                                      │     REST API + HTML Templates    │
                                      └──────────────┬──────────────────┘
                                                     │
                ┌────────────────────────┬───────────┼──────────────────┐
                │                        │           │                  │
      ┌─────────▼──────────┐  ┌─────────▼────────┐  │      ┌──────────▼─────────┐
      │   Connector Layer   │  │  Watcher Engine  │  │      │    MCP Server      │
      │ Logs|DB|Metrics|... │  │ Scheduler+Executor│  │      │  stdio JSON-RPC    │
      └─────────┬──────────┘  └─────────┬────────┘  │      └──────────┬─────────┘
                │                        │           │                  │
                └────────────────────────┼───────────┼──────────────────┘
                                         │           │
                          ┌──────────────▼───────────▼──────────────┐
                          │         SQLite Store Layer               │
                          │  DataSources | Logs | Watchers | Alerts  │
                          │     Servers | Metrics | Runs | Config    │
                          └─────────────────────────────────────────┘
```

### Key Design Decisions

- **SQLite for app storage** — Zero-dependency, single-file database with FTS5 for log search. No external database server required.
- **Connector pattern** — Pluggable data sources that register tools dynamically. Each connector implements `DataSource` interface and exposes tools to the AI agent.
- **Read-only database access** — All user database queries are validated to be SELECT-only via SQL AST parsing, with configurable timeouts and row limits.
- **MCP-first integration** — Instead of building a custom chat UI, OpenTrace exposes tools via MCP so you can use your preferred AI client (Claude Code, Cursor, etc.).

### Project Structure

```
cmd/opentrace/       # CLI entry point (web server, MCP server, VM agent)
internal/
  agent/             # AI agent loop, prompting, tool execution
  config/            # Environment variable configuration
  connector/         # Data source connectors (logs, database, server metrics)
  guardrail/         # SQL validation, safety checks
  llm/               # LLM provider abstraction (Ollama, Anthropic, OpenAI)
  mcp/               # MCP server implementation
  store/             # SQLite data layer, migrations, models
  vmagent/           # VM metrics collection agent (gopsutil)
  watcher/           # Automated monitoring engine
  web/               # HTTP handlers, templates, static assets
```
